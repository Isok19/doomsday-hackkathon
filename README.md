# CQA — система анализа качества диалогов

Локальная система для CQA Hackathon: Python + FastAPI, SQLite и интерфейс на HTML/CSS/JavaScript.
Frontend и API работают на одном сервере. Node.js, сборщик и Docker для запуска не требуются.

**Реализованы интерфейсы участников 1 и 4 и необходимая серверная интеграция. ИИ-анализ участника 3 пока не подключён.**
Приложение не создаёт вымышленные оценки: до подключения оценщика кнопка автоматической оценки недоступна.
При наличии настоящих результатов доступны доказательства, апелляции, решения и пересчёт.

## Быстрый запуск

Нужен Python 3.11 или новее. Проверено на Python 3.14 / macOS.
В терминале VS Code из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Windows PowerShell: создайте окружение командой `py -m venv .venv`, затем активируйте
`.venv\Scripts\Activate.ps1`. После активации команды `python` такие же.

| Адрес | Назначение |
| --- | --- |
| http://127.0.0.1:8000/ | Рабочий интерфейс системы |
| http://127.0.0.1:8000/docs | Swagger: проверка запросов API |
| http://127.0.0.1:8000/openapi.json | Машинное описание API |
| http://127.0.0.1:8000/health | Проверка запуска сервера |

Остановка — `Ctrl+C` в терминале сервера. Адрес `127.0.0.1` доступен на том же компьютере.
Размещение для команды и доступ с других устройств пока не настроены.

В VS Code также доступны задачи **Terminal → Run Task → CQA: сервер** и **CQA: тесты**
после установки зависимостей. Сервер остаётся в видимом встроенном терминале.

## Данные

Положите выданный `dialogs.json` в корень проекта. При запуске он проверяется и импортируется в
`data/cqa.sqlite3`. Повторный запуск с тем же набором не создаёт дубликаты.

В исходном DEV: **65 диалогов** — 60 чатов, 5 звонков; 35 RU, 15 KZ, 15 EN; **1268 сообщений**.
У звонков уже есть транскрипты и пять ссылок `audio_url`. Аудиофайлы отдельно не нужны для анализа текста.
Доступность записей зависит от внешнего сервиса; интерфейс предлагает плеер и открытие ссылки.

Если файла нет, приложение запускается с пустым списком. Его можно заполнить через кнопку
**Загрузить диалоги**. Принимается JSON в исходном формате ответа организаторов:
корневые поля `error`, `isSuccess`, `data`; внутри `data` — `dataset_group_id`, `total_records`, `records`.
Максимальный размер — 10 МБ. TXT, CSV и произвольные схемы транскриптов пока не поддерживаются.

В наборе сохраняются исходные ID, порядок реплик, роли, текст, временные метки и ссылки.
Для доказательств каждому сообщению добавляется `message_id`, определяемый по группе, ID диалога и позиции.
`position` начинается с 1; `timestamp` остаётся исходной строкой, без потери точности ISO-времени.

Наборы разделены по `dataset_group_id`. Импорт другого содержимого под уже существующим ID группы возвращает
409 и не затирает старые диалоги. Для независимого изменённого набора используйте отдельную БД через
`CQA_DATABASE_PATH`. Политика обновления уже оценённых транскриптов не вводилась без согласования.

## Папки и ответственность

```text
app/                         backend участника 2
  main.py                    запуск, подключение frontend, API чтения диалогов
  models.py                  формат диалогов организаторов
  storage.py                 SQLite, проверка и импорт данных
  routes.py                  API чек-листов, оценок, апелляций и загрузки
  workflow_models.py         схемы и проверка входных данных
  workflows.py               версии, хранение результатов, решения и арифметика
  checklist_seed.py          начальные восемь критериев из PDF
frontend/
  index.html                 общий каркас интерфейса
  app.js                     навигация между экранами
  participant-1/
    dialogs.js               список, фильтры, загрузка, транскрипт, аудио, запуск оценки
    results.js               баллы, N/A, секции, доказательства, история результатов
  participant-4/
    checklists.js            создание и редактирование критериев, весов, шкал, N/A
    appeals.js               подача апелляции и решение проверяющего
  shared/
    api.js                   общий HTTP-клиент, обработка ошибок, переход к доказательствам
    styles.css               общее оформление и адаптивная сетка
tests/
  test_api.py                импорт и сохранность исходных диалогов
  test_workflows.py          версии, оценки, N/A, доказательства, пересмотр и перезапуск
```

Оба интерфейса используют относительные запросы `/api/...`. При обычном запуске одного сервера
CORS не требуется. Стили и API-клиент общие; отдельные фронтенд-серверы для участников не нужны.
Структура модульная: дальнейшая адаптация для HTML-компонента Dynamics 365 возможна отдельно.
Интеграция с самим Dynamics 365 на этом этапе не выполнялась.

## Возможности участника 1

- Список диалогов с выбором набора, фильтрами языка/канала, поиском по ID и страницами по 12 записей.
- Загрузка JSON через интерфейс. Кнопка получения данных организаторов доступна после настройки URL сервера.
- Карточка с полным транскриптом, исходными ролями и временными метками.
- Плеер для звонков и ссылка на внешнюю запись; ошибки воспроизведения отображаются в карточке.
- Выбор сохранённого чек-листа и запрос автоматической оценки после подключения участника 3.
- Просмотр сохранённых оценок: ответ, вес, эффективный вес, баллы, объяснение, N/A и причина.
- Переход к доказательству с подсветкой сообщения; для пропущенного действия используются реплики проверенного участка.
- Итог, вклад секций, отдельные флаги нарушений, исходный и финальный результат.

## Возможности участника 4

- Создание чек-листа и редактирование имени, описания, секций и критериев.
- Добавление и удаление критериев, изменение формулировки, веса, типа ответа, ступеней шкалы и N/A.
- Каждое сохранение создаёт неизменяемую версию. Старые оценки сохраняют прежние правила.
- Проверка настроек на клиенте и сервере. Конкурирующее изменение версии возвращает 409.
- Апелляция по конкретному критерию: комментарий, исходная оценка и доказательства.
- Список обращений, фильтр статуса и карточка проверяющего с контекстом транскрипта.
- Подтверждение или изменение оценки с обязательной причиной; при изменении нужны новая оценка,
  обоснование и ссылки на сообщения. Для N/A обязательна причина неприменимости.
- Решение и пересчёт сохраняются, исходная оценка не перезаписывается.

Текущий прототип допускает одну апелляцию на критерий конкретной оценки. Повторная подача или повторное
решение возвращает 409. Повторное открытие закрытых обращений пока не предусмотрено.
Вход и регистрация отсутствуют, как разрешено заданием; подача и проверка — отдельные действия интерфейса.

## Правила расчёта

Начальная конфигурация перенесена из выданного `CQA_Chat_Quality_Checklist`.

| Критерий | Вес | Ответ |
| --- | ---: | --- |
| Установление контакта | 10 | Да / Нет |
| Выявление потребности | 15 | Да / Нет / N/A |
| Идентификация | 20 | Да / Нет / N/A |
| Корректная и полная консультация | 20 | 0, 5, 10, 15, 20 / N/A |
| Эмпатия и клиентоориентированность | 15 | Да / Нет |
| Управление диалогом, скорость и грамотность | 15 | 0, 4, 7, 10 |
| Завершение | 5 | Да / Нет / N/A |
| Грубые ошибки | 0 | Отдельный флаг Да / Нет |

Содержательные ответы должен определять модуль участника 3. Backend выполняет только проверку структуры
и арифметику для сохранения и пересмотра результатов:

- «Да» даёт полный вес, «Нет» — ноль; числовая оценка делится на максимум шкалы.
- Критерии с N/A исключаются; применимые веса нормализуются до 100.
- N/A допустим только по настройкам критерия с обязательной причиной. Смысловое соответствие причины
  правилу должен проверять оценщик или человек — арифметический модуль этого не утверждает.
- Итог округляется один раз до двух знаков. Показанные баллы отдельных строк округляются для отображения.
- При отсутствии применимых весовых критериев итог `null`.
- Флаг нарушения не обнуляет балл. Вклад секций показан в общей нормированной шкале.
- Порог первой реакции в 3 минуты, теги и вложения не входят в оценку.

## API

Точные типы и обязательные поля запросов доступны в Swagger и `app/workflow_models.py`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/health` | Состояние процесса |
| GET | `/api/capabilities` | Доступность оценщика и API организаторов |
| GET | `/api/datasets` | Импортированные наборы |
| GET | `/api/dataset` | Статистика выбранного набора |
| POST | `/api/datasets/import` | JSON организаторов в теле запроса |
| POST | `/api/datasets/fetch?group_id=...` | Получение набора по серверному URL |
| GET | `/api/dialogs` | Список диалогов |
| GET | `/api/dialogs/{conversation_id}` | Полный транскрипт |
| GET | `/api/checklists` | Последние версии чек-листов |
| GET | `/api/checklists/{id}?version=...` | Последняя или указанная версия |
| POST | `/api/checklists` | Создать чек-лист |
| PUT | `/api/checklists/{id}` | Новая версия; обязательный `base_version` |
| GET | `/api/evaluations?dataset_group_id=...&conversation_id=...` | История оценок диалога |
| GET | `/api/evaluations/{id}` | Правила, исходный и финальный результаты, апелляции |
| POST | `/api/evaluations/run` | Вызов подключённого оценщика; сейчас 503 |
| POST | `/api/evaluations` | Приём настоящего результата модуля участника 3 |
| GET | `/api/appeals` | Обращения и их статусы |
| GET | `/api/appeals/{id}` | Обращение с контекстом оценки |
| POST | `/api/appeals` | Подать апелляцию |
| POST | `/api/appeals/{id}/decision` | Сохранить решение и пересчитать итог |

Для списка диалогов: `dataset_group_id`, `language` (RU/KZ/EN), `channel` (agent chat/voice call),
`q` (часть ID), `limit` (1–100), `offset` (от 0). Ответ: `total`, `limit`, `offset`, `items`.
Карточка и статистика также принимают `dataset_group_id`. Без него выбирается исходный набор запуска.

Основные ошибки: 404 — объект не найден; 409 — конфликт версии/повторное действие/изменённый набор;
413 — слишком большой JSON; 422 — неверные параметры; 502 — ошибка внешнего сервиса;
503 — внешнее подключение отсутствует. Текст ошибки находится в `detail`.

## Подключение участника 3

См. [контракт оценки](docs/evaluation-contract.md).

Предусмотрены два способа:

1. Передать синхронную функцию `evaluator(dialog, checklist)` в `create_app(evaluator=...)`.
   Она возвращает список ответов по критериям. Тогда интерфейс разрешает запуск оценки.
2. Внешний модуль получает диалог и версию чек-листа через API и отправляет готовые ответы в
   `POST /api/evaluations`. Сохранённые оценки видны после повторного открытия карточки.
   Этот способ сам по себе не включает кнопку запуска оценщика.

Модель, ключи, база знаний компании, стоимость вызовов и качество анализа RU/KZ/EN ещё не определены.
В репозитории нет имитации ИИ или заранее подставленных оценок для демонстрации.

## Настройки окружения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `CQA_DATASET_PATH` | `dialogs.json` в корне | Входной JSON при старте |
| `CQA_DATABASE_PATH` | `data/cqa.sqlite3` в корне | Локальная БД |
| `CQA_CORS_ORIGINS` | пусто | Адреса отдельного frontend через запятую, если он нужен |
| `CQA_ORGANIZER_URL` | не задана | Полная подписанная HTTPS-ссылка из PDF организаторов |

Переменные задаются в окружении перед запуском сервера; `.env` автоматически не загружается.
В репозитории есть `.env.example` с именами переменных, без ключей и подписанной ссылки.
URL организаторов хранится только на сервере: frontend передаёт `group_id`, а не URL.
Подключение этого внешнего API ещё не проверено с действующей ссылкой; загрузка предоставленного JSON работает.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Для тестов нужен исходный DEV-файл `dialogs.json`. Тестовые SQLite создаются во временных папках.
Проверены 32 автоматических сценария: исходные транскрипты, импорт, пагинация, фильтры, версии,
N/A и веса, ссылки на доказательства, решения, сохранение истории после перезапуска и отсутствие оценщика.

Технические ответы в `tests/test_workflows.py` проверяют контракт и арифметику. Это не экспертные оценки
диалогов, они никогда не добавляются в рабочую БД при запуске системы.

В браузере проверены: список и фильтр KZ; сохранение новой версии чек-листа; отображение результатов;
создание апелляции; изменение оценки проверяющим; сохранение исходного итога и нового результата;
переход к доказательству. Проверки с техническими оценками выполнялись на отдельной временной БД.

## Сдача и ограничения

- Backend и frontend запускаются одной командой; интерфейс доступен на `/`, Swagger — на `/docs`.
- Контрольный набор можно загрузить через интерфейс без изменения кода.
- Критерии меняются через интерфейс; сохранение создаёт новую версию.
- Для полного показа оценки и апелляции нужны настоящие результаты участника 3.
- Точность ИИ-оценок, доступность внешних аудиозаписей и фактическое получение через API организаторов
  пока не подтверждены этой реализацией.
- Приложение предназначено для локальной демонстрации без авторизации. Общий хостинг команды не настроен.
- `.gitignore` исключает диалоги, PDF, SQLite, `.env`, окружение и прочие локальные данные из публикации.
  После клонирования команда получает DEV отдельно от организаторов.
